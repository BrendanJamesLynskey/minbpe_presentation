Part 1

Why Tokenisation?

LLMs never see your text — they see tokens

Tokens, not characters

A language model operates on a sequence of integer token ids drawn from a fixed vocabulary. Text must be tokenised on the way in, and token ids de-tokenised back to text on the way out.

Tokenisation is a separate, pre-trained stage. It has its own training set and its own algorithm (BPE), entirely distinct from the neural network.

The model's whole world is the token vocabulary — typically ~50K (GPT-2) to ~100K (GPT-4) entries.

"Tokenization is at the heart of much weirdness in LLMs."
raw text → [tokeniser] → token ids "hello world" ↓ [15339, 1917] (GPT-4 / cl100k_base) ↓ [transformer] ↓ next-token logits over the vocab

Tokenisation is the source of many quirks

Can't spell

  • Whole words become single tokens
  • The model never sees the letters inside
  • Character-level tasks suffer

Bad at arithmetic

  • Numbers split into odd chunks
  • "677" might be one token, "678" two
  • No consistent digit structure

Trailing whitespace

  • " hello" ≠ "hello"
  • A trailing space changes the tokens
  • Breaks completions in surprising ways

Non-English penalty

  • Rarer scripts → more tokens/char
  • Same meaning, longer sequence
  • More cost, less context budget

SolidGoldMagikarp: a Reddit username that appeared in the tokeniser's training data but barely in the model's. It earned its own token whose embedding was essentially never trained — feeding it in produced bizarre, unhinged behaviour. A pure tokenisation artefact.

Part 2

Unicode & UTF-8 Bytes

From abstract code points to a 256-symbol base vocabulary

Code points vs bytes

# A Python string is a sequence of Unicode CODE POINTS
ord("h")      # 104
ord("👍")     # 128077   (a single code point)
len("hello")  # 5 code points

# Using code points directly as tokens is a bad base:
#   - the vocabulary would be ~150,000 (and growing)
#   - the Unicode standard keeps changing
# Instead, encode the text to raw UTF-8 BYTES (0..255):
list("hello".encode("utf-8"))   # [104, 101, 108, 108, 111]
list("👍".encode("utf-8"))      # [240, 159, 145, 141]  (4 bytes)

UTF-8 encodes every Unicode code point into 1–4 bytes. ASCII stays 1 byte; emoji and rarer scripts take more. Crucially, every byte is in 0..255.

So the base vocabulary is just 256 tokens — one per possible byte. Small, fixed, universal. BPE then learns new tokens on top of these.

Try it — UTF-8 byte view

0UTF-8 bytes

Blue/green = single-byte (ASCII) characters. Amber = multi-byte characters where one code point spans several UTF-8 bytes — exactly why "1 character" is not the same as "1 token".

Part 3

The BPE Algorithm

Repeatedly merge the most frequent adjacent pair

get_stats — count adjacent pairs

def get_stats(ids, counts=None):
    """
    Given a list of integers, return a dictionary of counts of consecutive pairs
    Example: [1, 2, 3, 1, 2] -> {(1, 2): 2, (2, 3): 1, (3, 1): 1}
    Optionally allows to update an existing dictionary of counts
    """
    counts = {} if counts is None else counts
    for pair in zip(ids, ids[1:]):       # iterate consecutive pairs
        counts[pair] = counts.get(pair, 0) + 1
    return counts

One pass over the sequence. zip(ids, ids[1:]) yields every consecutive pair; we tally how often each one occurs. The winner is max(stats, key=stats.get) — the most frequent adjacent pair.

merge — replace a pair with a new id

def merge(ids, pair, idx):
    """
    In the list of integers (ids), replace all consecutive occurrences
    of pair with the new integer token idx
    Example: ids=[1, 2, 3, 1, 2], pair=(1, 2), idx=4 -> [4, 3, 4]
    """
    newids = []
    i = 0
    while i < len(ids):
        # if not at the very last position AND the pair matches, replace it
        if ids[i] == pair[0] and i < len(ids) - 1 and ids[i+1] == pair[1]:
            newids.append(idx)
            i += 2
        else:
            newids.append(ids[i])
            i += 1
    return newids

New ids start at 256 (just above the byte range) and increment: 256, 257, 258, … Each merge shrinks the sequence and grows the vocabulary by one.

Worked example — "aaabdaaabac", 3 merges

start (bytes): aaabdaaabac
merge aa→Z (256): ZabdZabac
merge ab→Y (257): ZYdZYac
merge ZY→X (258): XdXac

From the README: result is "XdXac" where X=ZY, Y=ab, Z=aa. With minbpe's 256 byte tokens allocated first, the final ids are [258, 100, 258, 97, 99] — 11 bytes compressed to 5 tokens.

merges & vocab — the two learned tables

# 'merges' records, in learned order, which pair maps to which new id
merges = { (97, 97): 256,      # aa -> Z
           (97, 98): 257,      # ab -> Y
           (256, 257): 258 }   # ZY -> X

# 'vocab' maps every id back to the raw BYTES it expands to
def _build_vocab(self):
    vocab = {idx: bytes([idx]) for idx in range(256)}      # 256 base bytes
    for (p0, p1), idx in self.merges.items():
        vocab[idx] = vocab[p0] + vocab[p1]                 # concat children
    for special, idx in self.special_tokens.items():
        vocab[idx] = special.encode("utf-8")
    return vocab

merges drives encoding (text → ids); vocab drives decoding (ids → bytes → text). Note merges is ordered: the order is the priority used at encode time.

Part 4

BasicTokenizer

train / encode / decode, straight over raw bytes

train — learn the merges

def train(self, text, vocab_size, verbose=False):
    assert vocab_size >= 256
    num_merges = vocab_size - 256

    text_bytes = text.encode("utf-8")   # raw bytes
    ids = list(text_bytes)              # list of ints 0..255

    merges = {}                                       # (int,int) -> int
    vocab = {idx: bytes([idx]) for idx in range(256)} # int -> bytes
    for i in range(num_merges):
        stats = get_stats(ids)                # count pairs
        pair = max(stats, key=stats.get)      # most frequent pair
        idx = 256 + i                         # mint a new id
        ids = merge(ids, pair, idx)           # apply it everywhere
        merges[pair] = idx
        vocab[idx] = vocab[pair[0]] + vocab[pair[1]]
    self.merges = merges   # used in encode()
    self.vocab = vocab     # used in decode()

encode — replay merges in learned order

def encode(self, text):
    text_bytes = text.encode("utf-8")
    ids = list(text_bytes)
    while len(ids) >= 2:
        stats = get_stats(ids)
        # pick the pair with the LOWEST merge index (earliest learned)
        pair = min(stats, key=lambda p: self.merges.get(p, float("inf")))
        if pair not in self.merges:
            break          # nothing left that we know how to merge
        idx = self.merges[pair]
        ids = merge(ids, pair, idx)
    return ids

Why lowest index first? Merges are hierarchical — later tokens are built from earlier ones (e.g. ZY needs Z and Y to exist first). Replaying in learned order reconstructs exactly the same tokens the trainer would.

decode — ids back to text

def decode(self, ids):
    # look up each id's raw bytes, concatenate
    text_bytes = b"".join(self.vocab[idx] for idx in ids)
    # then decode the bytes as UTF-8
    text = text_bytes.decode("utf-8", errors="replace")
    return text

errors="replace" is essential. An arbitrary list of token ids can produce a byte sequence that is not valid UTF-8 (e.g. a lone continuation byte). Without it, decode would crash; with it, the invalid bytes become the replacement character �.

Part 5

RegexTokenizer & GPT-2/4

Split first, so merges never cross category boundaries

The problem with naïve BPE

Plain byte-BPE will happily merge across word/punctuation/space boundaries — producing tokens like "dog.", "dog!", "dog?" as distinct units, and gluing common words to following spaces in inconsistent ways. This wastes vocabulary and hurts generalisation.

GPT-2's fix: split the text into chunks with a regex first, run BPE independently within each chunk, then concatenate. Merges can never reach across a chunk boundary.

Hello world 123 !!! ?

letters · numbers · punctuation · whitespace — kept in separate chunks before BPE

The GPT-2 & GPT-4 split patterns

# GPT-2 (from the released code)
GPT2_SPLIT_PATTERN = \
  r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""

# GPT-4 / cl100k_base (note: case-insensitive contractions, digits capped at 3)
GPT4_SPLIT_PATTERN = \
  r"""'(?i:[sdmt]|ll|ve|re)|[^\r\n\p{L}\p{N}]?+\p{L}+|\p{N}{1,3}| ?[^\s\p{L}\p{N}]++[\r\n]*|\s*[\r\n]|\s+(?!\S)|\s+"""

Both use the regex module (not re) for Unicode classes \p{L} (letters), \p{N} (numbers). GPT-4 made digits group in runs of at most 3 (\p{N}{1,3}) and made contractions case-insensitive — small but consequential changes.

encode_ordinary — per-chunk BPE

def encode_ordinary(self, text):
    """Encoding that ignores any special tokens."""
    # split the text up into chunks by the compiled regex pattern
    text_chunks = re.findall(self.compiled_pattern, text)
    ids = []
    for chunk in text_chunks:
        chunk_bytes = chunk.encode("utf-8")   # each chunk → its own bytes
        chunk_ids = self._encode_chunk(chunk_bytes)  # BPE within the chunk
        ids.extend(chunk_ids)
    return ids

train() mirrors this: it computes get_stats per chunk (accumulating into one shared dict), then merges across all chunks — but a merged pair can only ever come from within a single chunk.

Reproducing GPT-4 via tiktoken

import tiktoken
enc = tiktoken.get_encoding("cl100k_base")   # the GPT-4 tokeniser

# minbpe's GPT4Tokenizer wraps RegexTokenizer and loads cl100k's merges.
# It matches tiktoken exactly, even on tricky multilingual / emoji input:
text = "hello123!!!? (안녕하세요!) 😉"
# RegexTokenizer(GPT-4)  ==  tiktoken.cl100k_base   ✓ identical ids

Recovering the merges: tiktoken ships only the final {bytes: rank} table, not the ordered merge list. minbpe reconstructs the merge order with a small recover_merges() / bpe() routine — for each token, find the pair of lower-rank tokens that compose it, in rank order.

The byte-shuffle permutation: GPT-4 applies an "unfortunate (and likely historical?)" 1-byte permutation — the 256 base byte tokens are shuffled before BPE. minbpe recovers this permutation so the single-byte tokens line up with tiktoken's.

Part 6

Special Tokens & Comparison

Control tokens, and BPE-on-bytes vs BPE-on-code-points

Registering special tokens

# Special tokens live OUTSIDE the byte/merge range, with explicit ids.
# Example from GPT-2: a single end-of-text marker at id 50256.
special_tokens = { "<|endoftext|>": 50256 }
tokenizer.register_special_tokens(special_tokens)

# encode() must be told what to do with them, for safety:
tokenizer.encode(text, allowed_special="all")        # honour them
tokenizer.encode(text, allowed_special="none")       # treat as plain text
tokenizer.encode(text, allowed_special="none_raise") # raise if present

GPT-4 adds more: <|endoftext|> <|fim_prefix|> <|fim_middle|> <|fim_suffix|> <|endofprompt|> — used for document boundaries and fill-in-the-middle. They are isolated by string splitting before BPE, never learned as merges.

Both are BPE. The key split is what symbols BPE merges: bytes (tiktoken) vs code points with a byte fallback for the unknown (sentencepiece).

Practical tokeniser pitfalls

!

Whitespace & punctuation matter. A leading/trailing space, or punctuation glued to a word, changes the token ids — and therefore the model's behaviour and your token bill.

!

Never trust untrusted special tokens. Use allowed_special deliberately; an attacker who can inject <|endoftext|> can fracture your prompt structure.

!

Non-English costs more. Scripts under-represented in the merge training set tokenise into more, shorter tokens — inflating cost and shrinking effective context.

Key Takeaways

1

LLMs see tokens, not text. Tokenisation is a separate, BPE-trained stage — and the root cause of spelling, arithmetic, whitespace and multilingual quirks.

2

BPE is two functions. Count adjacent pairs (get_stats), merge the most frequent one (merge) into a new id, repeat. Bytes (0–255) are the universal base vocabulary.

3

Regex splitting + byte BPE = GPT. Add a category-aware split and special tokens and you reproduce GPT-4's tiktoken tokeniser exactly — in a few hundred clean lines.
